## ADDED Requirements

### Requirement: gRPC servers provide and generated clients use grpc method contracts
The Go, Java, C#, C++, Python and JavaScript/TypeScript extractors SHALL record `provides_contract` with context `grpc:<Service>/<Method>` for a method a server implements and `uses_contract` with that context for a call on a generated client, where `<Service>` is the proto service name without its package and `<Method>` is the method as the proto spells it: a stub's spelling SHALL be read back with its first letter upper-cased and, in C#, a trailing `Async` dropped. Servers SHALL be: a Java method taking a `StreamObserver<...>` in a class extending `<S>ImplBase`; a C# `override` method in a class whose base is `<...>.<S>.<S>Base`, taking a `ServerCallContext` or in a file using `Grpc.*` or with a base spelled through a `Grpc` namespace; a Python method `(self, request, context)` not starting with `_` in a class whose base is `<m>.<S>Servicer` with `<m>` a `*_pb2_grpc` module or `<S>Servicer` imported from one, or a same-file subclass of such a class; a C++ `override` member function defined in the body of a class deriving `<...>::<S>::Service` and taking a `ServerContext*`; each key of the object literal passed with `<x>.<S>.service` (or `<S>Service`) to `addService` in a JavaScript/TypeScript file importing `@grpc/grpc-js` or `grpc`; and in Go a method of the type T registered with `<P>.Register<S>Server(s, impl)` (`impl` being `&T{}`, `T{}`, `new(T)` or a local of the enclosing function assigned one) whose shape is `(context.Context, *<P>.Req) (*<P>.Resp, error)`, found anywhere in the registration's directory (a type registered for two services providing nothing), or a method taking a `<P>.<S>_<M>Server` stream that names itself. Clients SHALL be: Go `<P>.New<S>Client(c)` with one argument, or a name declared with the non-pointer type `<P>.<S>Client`, `<P>` imported from a generated-stub path (a path segment naming proto or grpc, or a `pb` package; never a connect-go `*connect` package), called with a context first, then the request, then only `grpc.X(...)` options; Java `<S>Grpc.new[Blocking|Future]Stub(c)` (with `.withX(...)` chained) or a name declared `<S>[Blocking|Future|BlockingV2]Stub` in a file that imports or names `<S>Grpc` in code (a comment does not count), any method but `with*`, `getChannel`, `getCallOptions`; Python `<m>.<S>Stub(c)` with `<m>` a `*_pb2_grpc` module or `<S>Stub` imported from one, `.future` / `.with_call` read through; C# `new <...>.<S>.<S>Client(c)` or a name declared with that type or a `using` alias of it, under the same `Grpc` condition as servers; JavaScript/TypeScript, in a file importing grpc, `new <S>Client(...)` or a name typed `<S>Client` with `<S>Client` imported from a generated-stub path, or `new <root>.<...>.<S>(address, credentials)` with `<root>` bound to a `grpc.loadPackageDefinition(...)` result, any method but the client machinery (`close`, `getChannel`, `waitForReady`, `make*Request`). A client SHALL be called inline or through a local, field, `self.x` or `this.x` bound to one (directly or through another name bound to one) anywhere in the file; a name bound to two services, or with any other binding in the file (a declared non-client type, any constructor or call that is no client constructor, an untyped parameter), records nothing. gRPC's `Health`, `ServerReflection` and `Channelz` services and OTLP's `TraceService`, `MetricsService`, `LogsService` and `ProfilesService` SHALL never be recorded, and a test source SHALL record nothing.

- **GIVEN** `cs.cartSvcClient.GetCart(ctx, req)` with field `cartSvcClient pb.CartServiceClient`, `pb.NewPaymentServiceClient(c).Charge(ctx, nil)` with `pb` imported from `example.com/demo/genproto`, `pb.RegisterProductCatalogServiceServer(srv, svc)` with `svc := &productCatalog{}` in `main.go`, and `func (p *productCatalog) GetProduct(ctx context.Context, req *pb.GetProductRequest) (*pb.Product, error)` in `catalog.go` of the same directory
- **THEN** the caller uses `grpc:CartService/GetCart` and `grpc:PaymentService/Charge`, and `GetProduct` provides `grpc:ProductCatalogService/GetProduct`

#### Scenario: A client name rebound to something else records nothing
- **GIVEN** in one file `client := pb.NewCartServiceClient(conn)` with `client.GetCart(ctx, req)` in one function and `client := dynamodb.NewFromConfig(cfg)` with `client.GetItem(ctx, in)` in another; likewise Python `cart_pb2_grpc.CartServiceStub(channel)` and `boto3.client("s3")`, TypeScript `new CartServiceClient(...)` and redis `createClient()`, Java `CartServiceGrpc.newBlockingStub(channel)` and `HttpClient.newHttpClient()`, C# `new Greeter.GreeterClient(channel)` and `_factory.CreateClient("x")`, each under one name
- **THEN** no gRPC fact is recorded in any of them

#### Scenario: Look-alike clients and servers record nothing
- **GIVEN** go-redis `redis.NewClusterClient(...).Get(ctx, k)`, a field `ilm *esclient.ILMClient`, `tracing.NewHTTPClient(t).GetJSON(ctx, "/x", url, &out)`, a connect-go `greetv1connect.GreetServiceClient`, channelz and OTLP trace clients, a TypeScript `PaymentClient` imported from `./payment-client` in a grpc-importing file, a Java `PaymentStub` with `PaymentGrpc` only in a comment, a Python `PaymentStub` class of the same file, C# `Elastic.Clients.Elasticsearch.ElasticsearchClient` and `new Stripe.StripeClient(...)` without `Grpc`, and C++ `folly::Service` / `base::Service` overrides taking no `ServerContext`
- **THEN** none of them records a fact

#### Scenario: Stub spellings read back to the proto name
- **GIVEN** a Java `productCatalog.listProducts(...)` on a `ProductCatalogServiceBlockingStub` field in a file importing `ProductCatalogServiceGrpc`, a C# `client.ChargeAsync(...)` on `new PaymentService.PaymentServiceClient(channel)` in a file using `Grpc.Core`, and a TypeScript `client.getCart(...)` on `new CartServiceClient(...)` imported from `../../protos/demo`
- **THEN** they use `grpc:ProductCatalogService/ListProducts`, `grpc:PaymentService/Charge` and `grpc:CartService/GetCart`

### Requirement: Message producers provide and consumers use topic contracts
The extractors SHALL record `provides_contract` with context `topic:<broker>:<name>` where code publishes to a topic or queue and `uses_contract` where code subscribes to one, broker `kafka`, `rabbitmq` (a queue on the default exchange), `sqs`, `sns`, `pubsub` or `jms`, so one name on two brokers is two contracts: Kafka (Spring `KafkaTemplate.send`, `new ProducerRecord`, `@KafkaListener(topics)`, `KafkaConsumer.subscribe(List.of(...))`, Kafka Streams `StreamsBuilder.stream/table/globalTable`; Kotlin `subscribe(listOf(...))` and `ProducerRecord(...)` with `org.apache.kafka` imported; Confluent .NET `Subscribe` on an `IConsumer`, `Produce` / `ProduceAsync` on an `IProducer`; Go sarama `ProducerMessage{Topic}`, `ConsumePartition` on a `Consumer`, `Consume(ctx, []string{...}, h)` on a `ConsumerGroup`, kafka-go `Message` / `Writer` / `WriterConfig` / `ReaderConfig{Topic}`, confluent `SubscribeTopics` on a `Consumer`; Python `KafkaConsumer(...)`, `subscribe` on a Kafka consumer and `send` / `send_and_wait` / `produce` on a Kafka producer; kafkajs `send({topic})` on a `.producer()` and `subscribe({topic|topics})` on a `.consumer()`), RabbitMQ on the default exchange (Spring `RabbitTemplate.convertAndSend(q, msg)` / `send(q, msg)` with two arguments, `@RabbitListener(queues)`, `setQueueNames`; RabbitMQ.Client `BasicPublish("" or string.Empty, q, ...)` and `BasicConsume(q, ...)` on a channel; amqp091 `Publish("", q, ...)` / `PublishWithContext(ctx, "", q, ...)` and `Consume(q, ...)` on a `Channel`; pika `basic_publish(exchange="", routing_key=q)` and `basic_consume(queue=q)` on a `.channel()`; amqplib `sendToQueue`, `publish('', q)`, `consume` on a `.createChannel()`), SQS (`QueueUrl` of AWS SDK v3 `SendMessageCommand` / `ReceiveMessageCommand`, boto3 `send_message` / `receive_message`, Spring `SqsTemplate.send`, `@SqsListener`), SNS (`TopicArn` of `PublishCommand`, boto3 `publish`), Pub/Sub (`topic(t).publish*` / `subscription` / `createSubscription`, Python `publish(topic_path(p, t))` / `create_subscription(topic=topic_path(p, t))`) and JMS (`@JmsListener(destination)`), each with its library in the file's imports. A receiver SHALL count only when every type the file declares its name with is the listed client type, or, declared with none, it is assigned from a listed constructor or call. The name SHALL be a string literal, the literal default of an env read, or a same-file name every binding of which is one such literal: any other binding of the name in the file (a parameter in any form, a bare arrow parameter, a destructuring pattern, a loop variable, a rebinding to another name or expression) SHALL make it read as nothing. An SQS URL SHALL read as its last path segment and an SNS ARN as its last `:` segment; a name outside `[A-Za-z0-9._-]{1,249}` or starting `amq.` SHALL record nothing. The source SHALL be the enclosing function; outside one, JavaScript uses `js_syntax::reading_scope_id` and Python and C# the file, and the other languages record nothing. A test source SHALL record nothing.

#### Scenario: Spring producers and consumers
- **GIVEN** `template.send("orders", 1L, order)` on a `KafkaTemplate` field, `rabbit.convertAndSend(QUEUE, shipment)` with `static final String QUEUE = "shipping-task"`, `rabbit.convertAndSend("exchange", "key", shipment)`, `mailer.send("not-a-topic", 1L)`, `@KafkaListener(topics = "orders")` and `@RabbitListener(queues = {"a-queue", QUEUE})`
- **THEN** the senders provide `topic:kafka:orders` and `topic:rabbitmq:shipping-task`, the listeners use `topic:kafka:orders`, `topic:rabbitmq:a-queue` and `topic:rabbitmq:shipping-task`, and the exchange send and the mailer record nothing

"orders"` with `_consumer.Subscribe(TopicName)` on an `IConsumer<string, byte[]> _consumer`

- **GIVEN** Go `const topic = "orders"` and `topic := cfg.Topic` before `&sarama.ProducerMessage{Topic: topic}`; TypeScript `const topic = 'orders'` with `topic => producer.send({ topic: topic })` and `function fwd2({ topic }) { producer.send({ topic: topic }) }`; Python `name = "orders"` with `for name in names: producer.produce(name, payload)`

## MODIFIED Requirements

### Requirement: Generic contract facts mint repo-free contract nodes
`resolve_contracts` SHALL read `provides_contract` and `uses_contract` raw relations whose context is `<kind>:<name>`, kind one of `table`, `label`, `header`, `claim`, `env`, `dynamo`, `grpc`, `topic`, and whose `target_label` is, for `table` and `label`, the database the extractor knows the name lives in (empty when it knows none) and, for `dynamo`, the comma-separated env variables whose default the name is (empty for a literal name). It SHALL mint one node per contract id, never passed through `make_id`: `table:<database>:<name>` and `label:<database>:<name>` with database `local` when none is known, `header:<name lowercased>`, `claim:<name>`, `env:<name>`, `dynamo:<name>` (case-sensitive), `grpc:<Service>/<Method>`, `topic:<broker>:<name>`. The node's kind SHALL be the contract kind, its label the name as a provider spells it (a user's spelling when this repo has no provider, then with `served: false` and no source anchor), with properties `name`, for tables and labels `database`, and for a DynamoDB table named by an env default `env` (every variable its facts name, in order of first appearance, comma-separated). Each provider SHALL get `handled_by` from the contract and `contains` from the provider's file; each user SHALL get `CONSUMES` to the contract. A fact with an unknown kind, no `:`, an empty name, a database spelled with `:` or spelled `local`, or a source no node names SHALL mint nothing and be counted. Extractors SHALL fold unquoted SQL identifiers to lower case and drop schema qualifiers (`public.users` is `users`) before emitting a fact. `route_resolution` SHALL report `contract_facts`, `contract_facts_unresolved`, `contracts_provided`, `contracts_external` and `contract_consumes`, through both stats JSON functions. These raw relations SHALL never become code-graph edges, and nodes of these kinds SHALL never be merged by semantic dedup.

#### Scenario: A table, a header and used-only contracts
- **GIVEN** `createUsers` providing `table:users`, `readTenant` providing `header:X-Tenant-Id`, `listUsers` using `table:users`, `sendTenant` using `header:x-tenant-id`, `claim:org_id` and `env:ML_BACKEND_URL`
- **THEN** `table:local:users` (kind `table`, database `local`) is `handled_by` `createUsers`, contained by its file and consumed by `listUsers`; `header:x-tenant-id` is labelled `X-Tenant-Id`, `handled_by` `readTenant` and consumed by `sendTenant`; `claim:org_id` and `env:ML_BACKEND_URL` are `served: false` with no anchor

#### Scenario: A DynamoDB table is its own kind
- **GIVEN** `storeTokens` and `putConnection` providing `dynamo:app-sessions` with env `DYNAMODB_TABLE_NAME` and `DYNAMODB_TABLE_NAME,TABLE`, `getConnection` using it, `remember` providing `dynamo:agent-notes` with env `DYNAMODB_TABLE_NAME`, and `getConnection` using `dynamo:Sessions`
- **THEN** `dynamo:app-sessions` (kind `dynamo`, no `database`, `env` `DYNAMODB_TABLE_NAME,TABLE`) is `handled_by` both writers and consumed by `getConnection`; `dynamo:agent-notes` is a separate node; `dynamo:Sessions` is `served: false` and no `dynamo:sessions` exists; no `table:` node is minted

#### Scenario: A malformed fact is counted, not minted
- **GIVEN** facts `queue:jobs`, `users`, `claim:`, a table whose database is `a:b`, a table whose database is `local`, and a header fact whose source names no node
- **THEN** no node is minted for them and `contract_facts_unresolved` is 6

#### Scenario: A contract fact is never a code-graph edge
- **GIVEN** a `uses_contract` fact whose `target_label` names a type the source file imports
- **THEN** `resolve_raw_relations` adds no edge

#### Scenario: Near-identical contract names stay apart
- **GIVEN** `table:formulation_values` and `table:formulation_value` anchored at the same migration lines, and likewise near-identical labels, headers, claims, env names and DynamoDB tables
- **THEN** semantic dedup merges none of them

### Requirement: One rule says which contract ids cross repositories
`is_bridged_contract(id)` SHALL be true for every `endpoint:`, `dynamo:`, `grpc:` and `topic:` id (a DynamoDB table's name is its whole address in an AWS account and region, a gRPC method's is its service and method, a topic's is its name on the broker: there is no database between to declare), for a `claim:` id whose name is not a standard JWT claim (`is_standard_jwt_claim`: a sorted static table of the IANA JSON Web Token Claims registry entries defined by RFC 7519 section 4.1, OpenID Connect Core 1.0, OpenID Connect Front-Channel Logout 1.0, RFC 7800, RFC 8693 and RFC 9449, retrieval date recorded; case-sensitive), for a `header:` id whose name is not a standard HTTP header, and for a `table:` or `label:` id in a named database; it SHALL be false for `table:local:` and `label:local:` ids, for every `env:` id, for a standard claim, for a standard header and for every non-contract id. The standard headers SHALL be a sorted static table of the permanent entries of the IANA HTTP Field Name Registry (lowercased, `*` dropped, retrieval date recorded) plus `x-request-id`, `x-real-ip`, `x-correlation-id`, `traceparent`, `tracestate`, `baggage`, and every `x-forwarded-*` name. `crossing_id` (with the declared databases, env and claim issuers) SHALL give the id a repo's contract crosses at: a member's repo-local table at its database's id; a `claim:<name>` of a member of a declared issuer `I` at `claim:I:<name>`, and nowhere when the name is an RFC 7519 section 4.1 registered claim (`is_registered_jwt_claim`: `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`); `claim:I:<name>` itself only for a member of `I`; a declared env id as itself; any other bridged id as itself; else none. `contract_spellings` SHALL give every id a repo may hold a crossing under: for `claim:I:<name>` a member's `claim:<name>` and nothing for any other repo, and nothing for an unscoped `claim:<name>` crossing in a repo declared in an issuer. With no issuer declared, claims SHALL cross exactly as `is_bridged_contract` says. Seam discovery and fuse, workspace `impact` and `path`, and change context's `cross_service` SHALL use these in place of any `endpoint:` prefix test. Proxy prefixes remain endpoint-only.

#### Scenario: Repo-local tables, env names and standard headers do not cross by themselves
- **THEN** `is_bridged_contract` is false for `table:local:users`, `env:NODE_ENV`, `header:authorization`, `header:x-forwarded-for` and `header:traceparent`, and true for `table:shop:orders`, `header:x-tenant-id`, `claim:org_id`, `dynamo:app-sessions`, `grpc:CartService/GetCart` and `topic:kafka:orders`

#### Scenario: Declarations make a repo-local table and an env name cross
- **GIVEN** database `shop` of api and ml, and `API_URL` declared for api
- **THEN** `crossing_id` gives ml's `table:local:users` as `table:shop:users`, `env:API_URL` as itself, and nothing for `env:NODE_ENV`; ml's spellings of `table:shop:users` are `table:shop:users` and `table:local:users`, web's only `table:shop:users`

#### Scenario: Standard JWT claims never cross
- **THEN** `is_bridged_contract` is false for `claim:iss`, `claim:sub`, `claim:aud`, `claim:exp`, `claim:nbf`, `claim:iat`, `claim:jti`, `claim:email`, `claim:name`, `claim:preferred_username`, `claim:scope`, `claim:client_id`, `claim:azp`, `claim:nonce` and `claim:sid`, and true for `claim:roles`, `claim:session_id`, `claim:tenant_id`, `claim:permissions` and `claim:EXP`

#### Scenario: A declared issuer scopes claims to its members
- **GIVEN** issuer `auth` of repos auth and web, and api in no issuer
- **THEN** `crossing_id` gives web's `claim:session_id` as `claim:auth:session_id` and auth's `claim:email` and `claim:scope` as `claim:auth:email` and `claim:auth:scope`, nothing for a member's `claim:sub`, `claim:iss`, `claim:aud`, `claim:exp`, `claim:nbf`, `claim:iat` or `claim:jti`, api's `claim:session_id` as itself, and nothing for api's `claim:email` or `claim:auth:session_id`
- **AND** web's spellings of `claim:auth:email` are `claim:email`, api's are none, web's of `claim:session_id` are none and api's are `claim:session_id`

#### Scenario: No issuer, no change
- **GIVEN** no issuer declared
- **THEN** `crossing_id` gives `claim:session_id` as itself and nothing for `claim:email`
