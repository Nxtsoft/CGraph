# Spring Boot Actuator endpoints are served by the build and the config

## Why

On the 2026-09-29 probe (`~/.agents/artifacts/2026-09-29/cgraph-multiservice-plan/`), M23 had no provider: passless-app's Ktor client calls `client.get("$baseUrl/actuator/health")` (`ApiClient.kt:44`), and idp serves it through `spring-boot-starter-actuator` (`idp-core/build.gradle.kts:41`) with `management.endpoints.web.exposure.include: health,info,metrics` (`idp-core/src/main/resources/application.yml:311`). No handler for it exists in idp's source, so `endpoint:GET /actuator/health` was `served: false` in idp's own graph and the seam had nothing to link.

## What Changes

- **The build file says the module is an Actuator web app.** `build.gradle.kts`, `build.gradle` and `pom.xml` are still extracted by their own grammars; `append_spring_actuator_facts` (new `spring_actuator.cpp`) also reads them, comments blanked. When the project's own `dependencies` block (Maven: `<dependencies>` outside `<dependencyManagement>`/`<plugins>`, scope not test/provided) has `org.springframework.boot:spring-boot-starter-actuator` on the runtime classpath (`implementation`, `api`, `runtimeOnly`, `compile`, `runtime`), a web starter (`-web`, `-webmvc`: servlet; `-webflux`: reactive), and the build applies the `org.springframework.boot` plugin (Maven: the Boot parent or `spring-boot-maven-plugin`), it emits a `spring_actuator` node at the dependency line and an `actuator_app` fact naming the module directory, the stack, and whether `micrometer-registry-prometheus` is a dependency.
- **The application config says what is exposed.** `detect_language` recognizes `application[-<profile>].{yml,yaml,properties}` directly under `src/main/resources` as `spring-config`. Its extractor reads the block-mapping YAML subset Spring configs use (nested maps, scalar lists, flow lists, `---` documents) and `.properties` (`#---` documents, `key[0]=` items, continuations), keeps the keys that decide paths (`management.*`, `server.port`, `server.servlet.context-path`, `spring.webflux.base-path`, `spring.mvc.servlet.path`, `spring.config.activate.on-profile`) under Spring's relaxed binding, resolves `${NAME:default}` to its default, and emits per document an `actuator_config` fact plus, when the document sets `management.endpoints.web.exposure.include`, an `actuator_exposure` node at that line.
- **resolve_contracts derives the routes.** `spring_actuator_routes` joins each module's facts and returns `file_route` facts, which mint endpoints like any other route. Rules (Spring Boot 4.1 reference, actuator/endpoints and actuator/monitoring, checked 2026-10-01): only `health` is exposed over HTTP by default; `exposure.include`/`exclude` lists with `*`, exclude winning; access from `management.endpoint.<id>.access`, `management.endpoints.access.default`, capped by `access.max-permitted`, with the pre-3.4 `enabled`/`enabled-by-default` booleans; `shutdown` and `heapdump` default to none; read-only keeps GET operations; `base-path` (default `/actuator`, `/` the root) and `path-mapping.<id>`; the context path (servlet) or `spring.webflux.base-path` (reactive) on the main port, `management.server.base-path` on a different management port, nothing for port `-1`; the discovery page at a non-root base path unless disabled; health's `{*path}`, configured groups, and `liveness`/`readiness` when `probes.enabled` is true. The base documents are one configuration and each profile (file or `on-profile` list) is the base overlaid by it, `.properties` over YAML, profile files over the base, later documents over earlier ones; the served routes are the union. An endpoint is `handled_by` the exposure node of the document whose `include` won, else the build file's `spring_actuator` node.
- `actuator_app` and `actuator_config` join the contract facts `resolve_raw_relations` skips. The index version is `logic-12` (graph output changes for Spring repos: config file nodes, actuator nodes, endpoints).

## Conservatively not modeled

No endpoint rather than a wrong one: endpoints needing a bean or dependency other than the Prometheus registry (flyway, liquibase, quartz, sessions, integrationgraph, httpexchanges, auditevents, startup, logfile, sbom, custom `@Endpoint`s); Jersey-only apps; a non-root `spring.mvc.servlet.path` (that configuration serves nothing); a deciding value whose placeholder has no default (that configuration serves nothing); version-catalog dependencies and `subprojects`/`allprojects` blocks; profile expressions (`!prod`, `a & b`) and combinations of active profiles, `spring.profiles.active`/groups; config outside `src/main/resources`; health component and additional paths (`/livez`); ports; Boot versions before 4 where `heapdump` defaulted to unrestricted.

## Contract that tests verify

- `spring_actuator_test.cpp`: detection of `application[-profile]` under `src/main/resources` only; the build fact needs the plugin, the web starter, and a runtime actuator dependency in the project's own block (not commented, not `testImplementation`, not `subprojects`), Groovy map notation and Maven (with a test scope refused); defaults (`/actuator`, `/actuator/health`, `{*path}`) handled by the build node; include lists, YAML lists and dotted keys, exclude, `*` with access defaults and the Prometheus registry, read-only and legacy `enabled`, relaxed `basePath`, path mapping, root and invalid base paths, port `-1`, context path, management port with its base path, discovery off, probes and groups, a servlet path, placeholders with and without defaults; profile files, `on-profile` documents, an expression applying to none, properties over YAML, `#---` documents, the handler of each route; through the real pipeline a Kotlin Ktor client consumes the served `endpoint:GET /actuator/health` handled by the exposure node at its line, and a repo that only mentions the actuator (deployment YAML, README, a non-Boot build) serves nothing.
- `detect_test.cpp`: `spring-config` for a profile config under `src/main/resources`; `k8s/base/application.yml` and `gradle.properties` stay undetected.
- `index_persistence_test.cpp`: `logic-12`.
- With the wiring (`detect.cpp`, `non_grammar_extractors.cpp`, `configured_extractors.cpp`, `contracts.cpp`, `graph_builder.cpp`) reverted, `spring_actuator_test` exits 1.

## Measured on the probe repositories

- ModSquad HTTP 24/29 linked, was 23/29: M23 is new; nothing lost. Turing HTTP 23/25, unchanged.
- `CONSUMES` edges: unchanged in all eight probe graphs. idp gains 11 served endpoints (`GET /actuator`, `/actuator/health`, `/actuator/health/{*path}`, its groups `core` and `redis`, `liveness`, `readiness`, `/actuator/info`, `/actuator/metrics` and `/{requiredMetricName}`, and `/actuator/prometheus` from the `local` and `production` profiles); `GET /actuator/health` is no longer `served: false`. The other seven graphs have the same node and link counts as before.

## Non-goals

- Ports and hosts: endpoint ids carry neither, so a management port is not distinguished from the main one.
- Any other framework-provided route surface.
